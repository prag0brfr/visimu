# aoeViewer

A fast viewer for AOE simulation result files.

**Version 2.2.2.** What it does:

- **Opens a study, not a file.** Add any number of result files, tick the runs
  you want, and compare them across a grid of plot tiles arranged in pages.
  Thirteen side panels decide what is drawn and how; the whole arrangement
  saves as a workspace.
- **Reads AOE text and HDF5.** Both dialects of the `.aoe` format; HDF5 read as
  declared where the file says what is in it, and otherwise inferred from any of
  the four tree conventions exporters use. Everything downstream —
  decimation, ISO filters, computed parameters, styles, workspaces — is
  identical either way.
- **Large files open at once,** including over a network share. An HDF5 file is
  not read when it is opened: its layout is worked out from dataset names, and
  written down so that opening it again costs a single read. Columns are fetched
  as they are drawn. A faster `.aoec` copy of any file over 8 MB is written
  afterwards by a separate process, so the window stays usable while it happens
  and every later open takes the cached path.
- **Compares runs on their own terms.** Filter runs by a value they hold
  constant, colour and dash them by independent keys, align them on an event
  rather than on the clock, and read any sample of any channel off the plot.
- **Derived channels** from an expression over the ones in the file, evaluated
  in the core.

The full manual is `doc/aoeViewer-2.2.2-User-and-Reference-Guide.pdf`, built
from the LaTeX source beside it.

The heavy work — parsing, computed parameters, plot decimation — happens in a
C++17 core. The user interface is Python with Qt (PySide6). The two meet at a
plain C ABI, so the core is one shared library that any CPython 3.8+ can load
through `ctypes`, with no build-time dependency on Python.

**Runs on Windows and Linux.** Nothing but a C++ compiler is required to build
the core; CMake is optional.

## Repository layout

Everything in the root is needed to build the software from scratch; nothing
else is kept there.

```
core/         C++17 core: parser, formulas, decimation, the C ABI
python/       the application and the scripting API
packaging/    PyInstaller spec, build script, generated icon
tools/        data generators, icon generator, benchmark
tests/        Python tests (the C++ ones live in core/tests)
build.sh      Linux/macOS build (no make needed)
build.bat     Windows build (MinGW, no make needed)
Makefile      Linux/macOS build, with header dependency tracking
CMakeLists.txt   optional alternative to make
```

Two directories are produced rather than kept: `build/` (compiled core and
PyInstaller work files) and `dist/` (the executable). Both are regenerated by
the build and are in `.gitignore`.

**Test data uses the `.aoe` extension**, which is what the file dialog filters
on and what the generators and both test suites now write. Generated data lands
in `data/`, which is also ignored. So is `*.aoec`, the binary sidecar written
beside a result file the first time it is opened -- derived data, rebuilt in
seconds, and megabytes apiece.

## Quick start

```bash
# 1. Build the core
./build.sh                # Linux/macOS
build.bat                 # Windows

# 2. Check it works
./build.sh test           # or: build.bat test

# 3. Run
PYTHONPATH=python python -m aoeviewer            # Linux/macOS
set PYTHONPATH=python && python -m aoeviewer     # Windows
```

To try it without real data:

```bash
python tools/gen_sample.py sample.aoe --sims 6 --rows 40000
PYTHONPATH=python python -m aoeviewer sample.aoe
```

## Building the core

### Linux and macOS

```bash
./build.sh          # builds build/libaoecore.so (or .dylib on macOS)
./build.sh test     # compiles and runs the C++ self-tests
./build.sh bench     # parser throughput benchmark
./build.sh pytest   # the Python tests, building the core first if needed
./build.sh clean
```

`g++`, `clang++` or `c++` is found on `PATH`. One that is not is named with the
`AOE_CXX` environment variable rather than by editing the script — nothing
machine-specific belongs in a file that is checked in and shared:

```bash
AOE_CXX=/opt/gcc-13/bin/g++ ./build.sh
```

It is plain `/bin/sh`, so it runs on a minimal container as readily as on a
desktop distribution, and it needs neither CMake nor make.

**Once you are editing the core regularly, prefer the Makefile.** `build.sh`
compiles every source in one command, which is right for a first build and
immune to stale objects, but it recompiles everything each time. The Makefile
tracks header dependencies with `-MMD -MP`, so it rebuilds only what a change
actually affects:

```bash
make                # builds build/libaoecore.so (or .dylib)
make test           # compiles and runs the C++ self-tests
make bench          # parser throughput benchmark
make CXX=clang++    # override the compiler
make clean
```

### Windows

`build.bat` uses MinGW-w64 and needs no CMake. If `g++.exe` is on `PATH` it is
found automatically. A portable MinGW-w64 that is not on `PATH` is named with
the `AOE_CXX` environment variable rather than by editing the script — nothing
machine-specific belongs in a file that is checked in and shared:

```bat
set AOE_CXX=C:\path\to\MinGW64\bin\x86_64-w64-mingw32-g++.exe
```

Then:

```bat
build.bat           :: builds build\aoecore.dll
build.bat test      :: runs the self-tests
build.bat bench     :: runs the benchmark
build.bat clean
```

The DLL is linked with `-static-libgcc -static-libstdc++` so it does not need
`libstdc++-6.dll` or `libgcc_s_seh-1.dll` beside it. This matters: without it,
`ctypes` reports only a bare *"DLL load failed"* when those are missing.

MSVC works too, if you prefer it:

```bat
cl /std:c++17 /O2 /EHsc /LD /DAOE_BUILD_SHARED /D_WIN32_WINNT=0x0A00 ^
   /Icore\include core\src\*.cpp /Fe:build\aoecore.dll
```

#### `_WIN32_WINNT`

Windows headers gate every declaration on `_WIN32_WINNT`, and MinGW-w64's
default for it differs between distributions. Too low, and the build fails with
errors that look like broken source rather than a missing setting:

```
error: 'SRWLOCK' does not name a type
error: 'AcquireSRWLockShared' was not declared in this scope
```

`core/include/aoe/win32.hpp` sets it to `0x0A00` (Windows 10) if nothing else
has, so this cannot bite whichever way you build — the flag above and in the
Makefile, `build.bat` and `CMakeLists.txt` is there to document the requirement,
not to carry it alone.

`0x0600` (Vista) is the real floor, set by the `SRWLOCK` and
`SleepConditionVariableSRW` calls in `platform_thread.hpp`; going below it gives
a plain `#error` saying so. `0x0A00` is what is used because the GUI already
requires Windows 10 through PySide6. To target something older, define
`_WIN32_WINNT` yourself — the header defers to it.

### With CMake (optional)

If you have CMake and would rather use it:

```bash
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
ctest --test-dir build
```

There is also an optional pybind11 module (`-DAOE_BUILD_PYBIND=ON`). It is not
what the application uses — see [Architecture](#architecture) — and it is
unverified, because pybind11 could not be reached from the environment this was
developed in.

## Installing the Python packages

### Normal networks

```bash
pip install --user numpy PySide6-Essentials shiboken6 pyqtgraph
pip install --user PyInstaller          # only for the standalone build
```

### Offline or behind a proxy

If `pip install` fails with a 403, your network is blocking PyPI. Two ways
around it, neither of which needs the target machine to be online.

**A. Company package index.** Many organisations run an internal Artifactory or
Nexus mirror. Point pip at it once:

```bash
pip config set global.index-url https://<mirror>/artifactory/api/pypi/<repo>/simple
```

The repository's *"Set Me Up"* page gives the exact URL. If it needs
credentials, generate an identity token in the web UI and include it in the URL.

**B. Download the wheels by hand.** This always works. Fetch them from any
machine with access (or from the mirror's web UI) into one folder, then:

```bash
pip install --user --no-index --find-links C:\wheels --no-deps ^
    numpy pyqtgraph colorama shiboken6 PySide6-Essentials
```

Three things to get right, each of which will otherwise waste your afternoon:

1. **Match the wheel to your interpreter.** For 64-bit Python 3.12 on Windows,
   filenames must contain `cp312-cp312-win_amd64` for compiled packages
   (`numpy`), `cp39-abi3-win_amd64` for `PySide6`/`shiboken6` — `abi3` means one
   wheel serves 3.9 through 3.13, so `cp39` is correct on 3.12 — and
   `py3-none-any` for pure-Python ones (`pyqtgraph`, `colorama`). Anything
   marked `manylinux`, `macosx`, `win32` or a different `cpXXX` will be rejected
   with *"not a supported wheel on this platform"*. `pip debug --verbose` lists
   every tag your interpreter accepts.
2. **`--no-deps` is required.** Without it pip tries to resolve dependencies
   against an index it cannot reach and backtracks through every historical
   release. With it, you supply the dependency list yourself — which is why
   `colorama` and `shiboken6` are named explicitly above even though you never
   use them directly.
3. **`shiboken6` and `PySide6-Essentials` must be the same version.** They are
   built as a matched pair and fail at import if they differ.

## Running

From a source checkout, `python/` must be on the import path:

```bash
# Linux/macOS
PYTHONPATH=python python -m aoeviewer [files...]

# Windows
set PYTHONPATH=python
python -m aoeviewer [files...]
```

Check the installation without opening a window:

```bash
PYTHONPATH=python python -m aoeviewer --version
```

which prints the package version, the core version, the path of the library it
loaded, and the worker-thread count.

To use a core library from elsewhere, set `AOEVIEWER_CORE` to its directory or
its full path.

### Command-line options

| | |
|---|---|
| `[files...]` | result files to open at startup |
| `--version` | print the package, core and library versions, and exit |
| `--selftest` | check that every dependency loads, report, and exit. Run this first when the application will not start |
| `--memory-limit MB` | cap on cached sample data (default 2048). Columns beyond this are dropped least-recently-used first and re-read on demand |
| `--build-cache FILE...` | write a `.aoec` sidecar for each named file and exit, without opening a window |

`--build-cache` is how the application builds sidecars for large files in the
background — it starts a copy of itself with this flag, and the window carries
on. It is also useful on its own, to warm a directory of results overnight so
that nobody waits for a first open:

```bash
PYTHONPATH=python python -m aoeviewer --build-cache study/*.aoe study/*.hdf5
```

It opens each file read-only, writes nothing but the sidecar, takes no lock that
would stop a solver writing to the source, and abandons a sidecar whose source
changes while it works. The exit status is the number of files for which no
sidecar was written, and a failure is never fatal: a sidecar only makes opening
faster.

## Building the standalone executable

```bash
python packaging/build_exe.py              # a folder (recommended)
python packaging/build_exe.py --onefile    # a single file
```

Output lands in `dist/`.

**PyInstaller does not cross-compile.** Build on Windows for a `.exe`, on Linux
for an ELF binary. Same sources, two builds.

**Folder or single file?**

| | Folder (default) | `--onefile` |
|---|---|---|
| Start-up | under a second | several seconds, every launch |
| Shipping | copy or zip the folder | one file |
| Antivirus | scanned once | unpacks ~60 MB per launch, rescanned |

Unless you specifically need one file, take the folder — the single-file build
extracts itself to a temp directory on every start, which is both slow and the
thing corporate antivirus tends to dislike.

The spec excludes the Qt modules this application never touches (WebEngine,
Quick/QML, Multimedia, 3D, SQL), which takes the bundle from roughly 150 MB to
roughly 70 MB. UPX compression is deliberately off, since packed binaries are a
common false-positive trigger.

The window icon comes from `packaging/aoeviewer.ico`, which is **generated**
rather than committed as a binary:

```bash
python tools/make_icon.py        # or: make icon
```

It draws a flight profile with a marker line as signed distance fields, 4x
supersampled, and writes every size Windows asks for (16 to 256 px) as 32-bit
DIB entries. No Pillow: an icon is not worth a dependency on a machine that
cannot reach a package index.

`build_exe.py` generates it automatically if it is missing, and the spec
refuses to build without it rather than quietly producing an unbranded
executable. It is applied in **two** places, because they are separate things:

- embedded as a resource in the `.exe`, which is what Explorer, the taskbar
  shortcut and the properties dialog show;
- bundled as a data file and applied with `setWindowIcon()` at startup, which
  is what the title bar and the *running* taskbar button show. Only doing the
  first leaves a branded file that opens an unbranded window.

**If Explorer still shows a generic icon** while the title bar and taskbar are
correct, the executable is fine and the shell's icon cache is stale. Explorer
caches an icon per file *path*, and a path first seen when the executable had
no icon keeps the generic one however many times you rebuild. The build now
calls `ie4uinit.exe -show` afterwards to refresh it; if a stubborn entry
survives that, log out and back in, or run:

```bat
ie4uinit.exe -ClearIconCache
taskkill /f /im explorer.exe && start explorer.exe
```

You can confirm the resource really is there rather than guessing — a correct
executable has both `RT_ICON` and `RT_GROUP_ICON` entries in its `.rsrc`
section, which is what this one has (7 images, 1 group). The build also writes
a version resource, so Properties shows a name and version instead of blanks.

Note that the core library must already be built — `build_exe.py` checks and
tells you if anything is missing.

### The build checks itself

After building, `build_exe.py` launches the result once with `--selftest` and
prints the outcome. The self-test imports NumPy, PySide6, pyqtgraph and the core
library one at a time and reports each separately, so a bundle that builds
cleanly but cannot start fails here — with the whole traceback — instead of at
the user's desk behind a dialog box that truncates it.

You can run it by hand at any time:

```bash
dist/aoeviewer/aoeviewer --selftest      # folder build
dist/aoeviewer --selftest                # --onefile build
```

Pass `--no-selftest` to skip it.

### When the executable will not start

Two options exist for the two failures that actually happen on locked-down
machines:

```bash
python packaging/build_exe.py --debug
```

builds with a console window attached, so the startup traceback is readable
rather than being cut short by a message box.

```bash
python packaging/build_exe.py --onefile --runtime-tmpdir "%LOCALAPPDATA%\aoeviewer"
```

changes where a single-file build unpacks itself. By default that is `%TEMP%`,
and a machine with AppLocker configured to forbid executing code from `%TEMP%`
will block every extension module in the bundle. The symptom is misleading —
usually `Importing the numpy C-extensions failed`, sometimes a Qt plugin error —
because what is reported is the first import that happened to need a DLL, not
the policy that blocked it. The folder build does not have this problem at all,
which makes it the better answer if you have the choice.

## Using it

The window has a tab rail down the left edge, a panel beside it, and a grid of
plot tiles filling the rest. A bar above the grid manages pages and tiles; a
status bar along the bottom carries the current summary, a progress bar while
the application is busy, the crosshair readout and the size of the sample cache.

One tile is **active** — marked by an accent border — and every per-tile control
acts on it. Click a tile to make it active; double-click to make it active, fit
it, and bring PARAMS forward.

### The panels

Thirteen panels, selected from the rail. Six act on the active tile only
(PARAMS, STYLE, SCALE, SYNC, 3D, TEXT); the rest apply to everything.

**DATA** — add and remove files, and tick which runs to plot. Every run of the
first file is ticked automatically, so something is on screen straight away.
*Reload* re-reads the selected files from disk, or every open file when nothing
is selected. Nothing polls the disk: whether the data on disk is finished is a
question only the person running the solver can answer, so re-reading happens
when you ask and at no other time.

Double-click a file or run to **rename** it, or use the right-click menu. Only
the label changes — the identity a colour or a saved workspace is keyed on is
untouched, so a renamed run keeps its style. Hovering shows the full path, and a
renamed run also shows the name the file itself gives it.

Runs are often named `X.Y.Z` and often number in the hundreds, so the box above
the tree **filters** them:

- `2.1` shows `2.1.3` and `1.2.1` alike — the match is on any part of the name,
  because the middle field is as often the interesting one as the first.
- `2.*.3` matches `2.1.3` and `2.57.3`: a pattern containing a wildcard is
  matched against the whole name instead.
- Matching ignores case, and a file whose own name matches keeps all of its runs.

The filter is a view and nothing more: a hidden run keeps its tick and keeps
plotting. While one is typed, *Plot all* and *Plot none* say *(shown)* and act
only on the rows on screen.

**PARAMS** — pick the x parameter and tick y parameters for the active tile.
Channels already on the tile are listed first, in the order they were ticked;
the rest keep the file order, and unticking one puts it straight back among
them. The filter box accepts wildcards: `AL*` matches `ALPHA` and `ALT`.
Filtering only hides rows — a selected name that does not match stays selected
and reappears as soon as the filter lets it through. **Right-click a parameter**
to alias it, make it the x axis, or copy its name.

**COMPUTE** — define derived channels from the ones in the file. See
[Computed parameters](#computed-parameters).

**ALIAS** — give a channel a readable display name without touching the file,
so the application shows "Load factor" while still reading `NZ`.

**ISO** — filter runs by parameters that are constant within a run (Mach
number, mass, altitude). **Several filters can be active at once and they
combine with AND**, so adding one narrows the set: Mach 0.75 *and* 180 t.

The panel is a tree, one collapsible node per parameter over its own values, so
every filter and everything selected in it is visible at once:

```
 v MACH      3/12
     0.70
     0.75
     0.80
 > WEIGHT    all 5   grouped
```

A parameter's checkbox is a **select-all for the values under it**: it ticks
every value (or every interval, when the parameter is grouped), unticks them
all, and shows a partial tick when some but not all are on. The filter's own
on/off flag is on the right-click menu as *Use this filter*; switching it off
keeps the values you ticked, which makes "with and without this" a two-click
comparison, and the row says `paused`. Each row carries a count (`3/12`,
`all 5`, `none of 8`) and hovering names the selected values. Nodes stay open
across refreshes, and one that no longer appears in any loaded file says so.

**Group…** opens the interval editor for the selected parameter, for a sweep
with more distinct values than you want to read. Choose the number of groups —
never more than there are values — and it splits the observed range evenly; then
edit any boundary and the rest follow. Editing moves an *edge*, not an interval:
a row's From and the row above's To are the same number, so overlaps and gaps
cannot be expressed. Pulling an outer edge inwards is how you deliberately
exclude an outlier. The **Values** column counts what each interval actually
claims, so an interval that catches nothing says so before you close the dialog.

If a file is loaded whose values fall outside intervals set up for the old ones,
the parameter's row says how many fall outside every group — those runs are
being filtered out, and without the note the plot simply comes back short. The
grouping is reported rather than silently redrawn; **Distribute evenly** is the
one-click fix.

**STYLE** — how the tile and its curves look.

- *Tile display* — legend, grid, log Y and point markers.
- *Colour by* — parameter, simulation, or ISO value; this sets the colour only.
  **Parameter is the default**: a tile is nearly always asked which quantity a
  line is, and colouring by run answers a different question — one a
  twenty-five-run study answers with twenty-five colours that name nothing you
  chose. Styles are keyed by name, not by list position, so loading another file
  never recolours what is already on screen.
- *Style by* — None, File, Simulation or ISO; this sets the dash pattern and
  marker independently of colour. *None* makes the dash follow the colour key.
  *File* is the usual partner for *Colour by Parameter*: one colour per
  quantity, one dash per result file. *Apply encoding to all tiles* copies both
  choices, including the ISO parameter each is keyed on.
- Two tables, *Colour* and *Line*, each scrolling when the list is long. Colour
  rows are the identities of *Colour by*, Line rows those of *Style by*. In ISO
  mode the rows are the ISO values, so you set the colour for "MACH = 0.75" once
  and every run at that Mach uses it.
- Global line width and marker size, plus *Re-assign palette* to start over.
- *Legend* — which corner it sits in, and which parts each entry is built from
  (parameter, ISO value, file, run). The default is the parameter name alone.
  **Turning File and Run off merges identical entries**, which turns a fifty-run
  ISO plot into one row per ISO value instead of fifty rows saying the same
  thing. *ISO* writes every ISO identity a curve carries — the colour's and the
  dash's, once each if both key on the same parameter — so *Colour by Parameter*
  with *Style by ISO* reads `ALT | MACH = 0.75`, ordered by value or interval.
  The dash and marker are not spelled out in words: the legend draws a sample of
  the actual curve, which carries both. **Apply legend to all tiles** copies the
  whole lot onto every tile on every page and says how many it changed.

The legend and any text captions can be dragged wherever you want them.

**SCALE** — fix the displayed range of either axis. While unlocked the four
boxes follow the plot as you zoom and pan, so ticking *Lock* freezes exactly
what you are looking at. A locked axis is a hard bound, not a starting position:
the view box is given matching limits and the mouse is disabled on that axis, so
a drag or a wheel cannot take you back outside it.

*Apply X range to every tile with the same X axis* attaches the range **to the
variable** rather than to the tiles that exist at that moment, so a tile you
fill in afterwards is scaled the same way — setting up the scales first and then
populating the grid is the normal order of work. The *Constrained variables*
list shows what is declared, and *Unlock both and auto-fit* releases the
constraint on this tile's parameters as well as unlocking the tile.

**SYNC** — align the runs of a tile on an event rather than on the clock.

A channel logged over several runs of the same manoeuvre carries that manoeuvre
at a different place in each run, because each recording started at a different
moment. Plotted against TIME the curves are the same shape smeared sideways.
SYNC shifts each run along the x axis so that a chosen event lands in the same
place for all of them. Name the channel the event is about, say what counts as
the event, and say where it should end up:

| Condition | What it finds |
| --- | --- |
| first rises above / falls below | the first sample past a level you give, interpolated between samples |
| first crosses | the same, in whichever direction the channel approaches it from |
| first starts to rise / fall | no level needed: the first move of 2 % of the channel's own range away from where it started |
| reaches its maximum / minimum | the extreme of the run |

| Move the event to | Result |
| --- | --- |
| zero | the axis reads as time since the event |
| the first run's event | everything moves onto the first run, keeping the original axis values meaningful |
| a value I choose | for lining two tiles up on the same reference |

A car accelerating from rest, logged five times: choose SPEED, *first rises
above*, 0.5, and *zero*. Every run is then drawn with x = 0 at the moment it
began to move.

Three things worth knowing. The event is found by **interpolating** between the
two samples either side of it rather than taking the nearer one; two runs logged
at different rates would otherwise align only to the sampling interval, which
shows up as a step between them. Where the crossing falls inside a gap — NaN,
which is what an unreadable token becomes — the first readable sample past the
level is reported instead, because there is nothing to interpolate across. And a
run in which the event never happens is **left where it is, and counted**: the
panel says "7 run(s) aligned, 1 left unaligned because the event was not found
in them", and *List the events* names them with the x value found in each.
Hiding such a run would lose data; shifting it by a guess would be a lie.

The alignment is per tile, so one page can hold the aligned comparison beside
the raw one — the arrangement that shows what the alignment did. *Apply to every
tile on this page* copies it across. The tile title says so too:
`ALT = f(TIME)  [0 = SPEED event]`. Markers and bands are evaluated in each
run's own axis, so they keep meaning "this instant in this run" and travel with
the curve they mark.

**3D** — turn the active tile into a rotatable projection of three channels:
pick X, Y and Z, then spin it with the two sliders, the Iso/Top/Front/Side
presets, or with the mouse. In Pan mode, navigation follows the convention every
simulation viewer shares:

| | |
|---|---|
| drag | turn |
| middle-drag, or Shift+drag | slide |
| right-drag, or Ctrl+drag | zoom |
| wheel (Zoom mode) | zoom |
| double-click, `Ctrl+0` | frame everything again |

The zoom runs from 1000× in to 5000× out, so pulling right back from a long
trajectory is possible, and it survives a rotation.

**The grid is drawn on the back walls.** An orthographic projection has no
perspective cue, so without a reference surface a point in the middle of the
frame could be anywhere along the line of sight, and a trajectory that loops
back on itself is guesswork. Grid lines go on the three faces of the data box
that lie *behind* the trajectory, recomputed from the view direction so they
swap as you turn the object and never draw over the data — the convention
MATLAB, Origin, Tecplot, gnuplot, mplot3d and Plotly all share. Tick values sit
on the three box edges radiating from the far corner, coloured by axis. It is
one checkbox, on by default; a very dense trajectory is occasionally clearer
bare.

Orientation comes from a **triad in the bottom-left corner** — three labelled
arrows, X red, Y green, Z blue, turning with the view, as in ParaView, Tecplot,
EnSight and every CAD package. The labels stay `X`/`Y`/`Z` rather than becoming
parameter names, so the triad does not turn into a second legend; hover it for
the channel on each axis and its range. There is no wireframe box around the
data: a cube drawn through the middle of a trajectory competes with the curves
while answering a question the triad answers better.

Each axis is normalised to the cube, so three channels with unrelated units —
metres, radians, Mach — produce a readable shape instead of a needle, and the
bounding box carries each axis's real range.

**INSPECT** — two sub-tabs, answering "what are the numbers here?" one curve
and one sample at a time.

*Statistics* — min, max, mean, standard deviation and sample count per curve,
over **the range currently shown**, updated as you pan and zoom: when you have
zoomed into a manoeuvre, the peak load factor *there* is the question. A
checkbox switches to the whole channel, and the table copies to the clipboard
tab-separated.

*At a point* — switch the mouse to Inspect, then **click** a curve to list every
channel of that run at that x value, with the file and run named — the "what was
everything else doing here?" question a single plot cannot answer — or **drag**
across the tile for a dashed line that reports d*y*/d*x*, both deltas, the two
endpoints and the inverse slope. A drag shorter than about six pixels counts as
a click, so the two gestures do not fight each other. The sample being reported
is marked with a red dot, since the click lands on whichever curve was nearest,
which is not always the one you were aiming at.

**AREA** — shaded x bands, for marking phases of a manoeuvre, with an optional
caption at the top of the band. On a tile plotted against the band's own
parameter it is a vertical stripe; **on any other tile the matching span of each
curve is highlighted instead**. A band on `TIME` from 10 s to 20 s has no
vertical stripe on `ALTITUDE = f(RANGE)`, but it does have a piece of each curve
— and that piece says where the aircraft actually was during those ten seconds.

**MARKERS** — a condition on one parameter, drawn on every tile. On a tile
plotted against that same parameter it is a vertical line; **on any other tile
it becomes a dot** on each curve, at the sample where the condition holds. Put a
marker at `TIME = 5` and you can see where five seconds falls on
`ALPHA = f(NZ)`. A marker outside a run's range is not drawn for it rather than
clamped to the nearest end — a clamped dot would claim a condition was met that
never was.

Areas and markers are **global**: an annotation is attached to a parameter, not
to a tile, so it appears on every page at once. New ones default to the middle
of the current view. Both are drawn **over** the curves, because the point of a
band is to see which part of the trace it covers.

**TEXT** — captions on the active tile: text, size, colour, bold, and a position
given as a fraction of the tile, with nine one-click presets. Because the
position is a fraction rather than a data coordinate, a caption stays where you
put it when the plot is panned or zoomed. Deliberately per-tile, unlike markers
and areas: those describe a *condition* and belong wherever it can be seen,
while a caption describes this particular picture. *Copy to all tiles* is there
when you do want it everywhere.

Anything drawn **over** the curves — the crosshair readout, the slope figure, a
text note, a 3D tick — sits on an opaque panel in the plot's own background
colour, so text never reads as part of a trace running under it.

### ISO values on screen

ISO values are written the same way everywhere they appear — a tree row, a
legend entry, a generated interval name — because every character there is one
the data does not get: two decimals with trailing zeros trimmed (`0.75`, `3`,
`180`, `1234.57`), and a power of ten at either end of the range where two
decimals stop saying anything (`1.23e-3`, `5e-5`, `1.23e6`, `-2.5e8`). The
rules are at the top of `core/include/aoe/iso.hpp`, where `ISO_DECIMALS` is the
one place to change if you want more.

Two decimals cannot tell `1.1701` from `1.1703`, so a parameter whose values are
that close shows repeated rows. Each still ticks independently — a row carries
the value it stands for, not its label — but they read alike.

### Mouse modes

Four mutually exclusive modes in the toolbar (`Ctrl+1` … `Ctrl+4`). The inactive
ones are genuinely off: in Select and Inspect the view box has mouse interaction
disabled entirely, so a stray drag cannot pan a plot you only meant to click.

| Mode | |
|---|---|
| **Select** | click a tile to make it active; the view does not move |
| **Inspect** | click a curve to read every channel of that run at that point |
| **Pan** | drag to move; the wheel is disabled. On a 3D tile, Pan means rotate |
| **Zoom** | the wheel zooms, and a drag zooms — see below |

In **Zoom**, the shape of the drag chooses which axes it applies to:

| Drag | Result |
| --- | --- |
| an area | zooms into that rectangle |
| a flat line across | zooms the **x axis only**, leaving y exactly as it was |
| a line up and down | zooms the **y axis only**, leaving x exactly as it was |

The rubber band shows which of the three it has decided — spanning the full
height of the tile for an x-only zoom, the full width for a y-only one — so the
gesture is confirmed before you release the button. There is no mode to select
and nothing to hold down.

The reason for the two constrained gestures is that the unconstrained one is
usually not what is wanted: a stretch of x with y untouched is the common case,
and doing that with a rectangle means dragging the full height of the tile by
eye and getting it slightly wrong, which rescales y by a few per cent for no
reason and makes two tiles that should be comparable no longer comparable. A
drag of only a pixel or two does nothing at all, so a twitch while clicking
cannot zoom the view by a factor of a hundred.

Clicking a curve in Inspect mode, or dragging out a slope, brings the INSPECT
panel forward.

### Fitting

**Double-click any plot to fit it**; `Ctrl+0` fits every tile. A tile also
frames itself the moment it acquires its first curve, and then leaves the frame
alone — a rebuild happens for all sorts of reasons that say nothing about what
should be on screen, and re-fitting on every one would throw away whatever you
had zoomed in on. Emptying a tile and filling it again fits the new contents.

Fitting uses **what is in the window**, not what is in the file: with x pinned
to a range, y is fitted to the samples that fall inside it, otherwise the part
you are examining ends up as a flat line at the bottom of a tile scaled to a
manoeuvre elsewhere in the run. Locked axes are honoured — a lock is a
deliberate constraint, often applied across every tile sharing a variable so
they can be compared, so fitting moves only the free axes.

### Pages and tiles

Page and tile management sits on a bar directly above the grid:

- **Page** — previous/next, a dropdown and a name box. `+` and `−` add and
  remove pages, `◄` `►` reorder them, and **Duplicate** copies the current page
  with every tile on it, names the copy `<name> (2)`, inserts it after the
  original and makes it active. Duplicating a duplicate gives `(3)` rather than
  `(2) (2)`. Removing a page asks first, and says how much is on the one it is
  about to remove.
- **Grid** — a Word-style dropdown: sweep the mouse over the 5×5 matrix and
  click to set the layout. Cells beyond 25 tiles are greyed out.
- **Tile** — arrow buttons swap the active tile with its neighbour, and
  Copy/Cut/Paste/Clear move a tile's whole configuration.

Each tile is titled with what it is plotting, as `ALPHA, NZ = f(TIME)`. Every
selected y is named, and a long list wraps onto a second line. The axes
themselves are left unlabelled: the title already carries the names, and the
units reach the reader through the tick values and the INSPECT tables.

Moving the mouse over a plot shows the value of every curve at that x in the
status bar.

### Workspaces

`Ctrl+S` and `Ctrl+L` save and load a workspace: file paths, pages and their
names, tiles, selections, computed parameters, aliases, *Colour by* / *Style
by*, the names you gave files and runs, the interface size, the theme, and every
colour and line style, as JSON (schema version 3, plus `app_version`).

Display names are keyed by identity rather than by position — a file by its
path, a run by the core's `<file>::<id>::<ordinal>` key — because a workspace is
routinely opened against files that have since gained a run or lost one, and a
name pinned to "the seventh run" would then land on whichever run happens to sit
there. A name whose file or run is not in the data is dropped without comment.

**Reusing a workspace against another study** — remove the old file, add the new
one — keeps every tile's axes. Closing a study leaves its formulas and aliases
defined, so that opening the next one does not throw away the work set up for
it; but a formula over columns that are not loaded evaluates to nothing and an
alias resolves to a channel no file carries, so neither is a candidate for an
axis while nothing is open.

Workspaces written by earlier versions open unchanged: anything they do not
mention takes its default, and a workspace that names an interface size keeps
the size it was saved at.

### Lists built for the size these files come in

The PARAMS filter refilters 400 ms after the last keystroke rather than on every
one, because a 585-channel file is several hundred rows hidden or shown per
letter. The ISO tree shows at most 400 values per parameter and still filters on
the rest. A file of more than 200 runs opens *closed* in DATA — expanding a node
is what makes Qt build view items for its children — and whichever way you leave
it is remembered by path, so it survives a reload and a rename.

A rebuild that changes nothing draws nothing: the curve groups are adopted and
their points reused, the plot's own settings are written only when one of them
differs, and the markers and bands keep their items unless the annotations, the
x channel, the drag mode or the curves have moved.

## Computed parameters

Define a name and an expression in the **Compute** tab. The expression is
validated as you type, before any data is touched.

```
LOAD_FACTOR  =  NZ * 9.80665
DRIFT        =  HEADING - HEADING[TIME=first]
HIGH_ALPHA   =  if(MACH > 0.8, ALPHA, nan)
ENERGY       =  0.5 * MASS * (VX^2 + VY^2)
NZ_NORM      =  NZ / max(NZ)
```

| | |
|---|---|
| Arithmetic | `+` `-` `*` `/` `%` `^` (right-associative) |
| Comparison | `<` `<=` `>` `>=` `==` `!=` — yield 1.0 or 0.0 |
| Logic | `&&` `\|\|` `!` |
| One argument | `abs sqrt sin cos tan asin acos atan exp log log10 floor ceil round sign deg rad` |
| Two arguments | `min max atan2 pow mod hypot` |
| Three arguments | `clamp(x, lo, hi)` `if(cond, a, b)` |
| Series | `deriv(Y,X)` `integ(Y,X)` `lowpass(Y,X,fc)` `highpass(Y,X,fc)` `movavg(Y,N)` `delta(Y)` |
| Reductions | `min(Y)` `max(Y)` `mean(Y)` — one value per run |
| Constants | `pi` `e` `nan` |
| Lookup | `NAME[COND=value]`, `NAME[COND=first]`, `NAME[COND=last]` |

**Series functions** look at the whole channel rather than one sample at a time:

```
PITCH_RATE   = deriv(THETA, TIME)
DISTANCE     = integ(VTAS, TIME)
ALPHA_SMOOTH = lowpass(ALPHA, TIME, 2.0)
ALPHA_NOISE  = highpass(ALPHA, TIME, 5.0)
```

**Reductions** collapse a channel to a single value, held flat across the run so
it combines with per-sample channels by ordinary arithmetic. Each run is reduced
separately, so `NZ / max(NZ)` normalises every run against its own peak rather
than against the study's.

The number of arguments decides which `min`/`max` you get: `max(NZ)` is the peak
load factor of the run, `max(NZ, NY)` is the larger of the two at each instant.

```
NZ_NORM      = NZ / max(NZ)
NZ_ENVELOPE  = max(NZ, NY)
ALPHA_EXCESS = ALPHA - mean(ALPHA)
```

**Lookup** takes the value of a channel at one sample. `ALPHA[TIME=12.5]` is
alpha at the sample nearest twelve and a half seconds. In place of a number,
`first` and `last` name the ends of the run — use these when runs have different
lengths and no single number would mean "the end" for all of them. Leading and
trailing gaps are skipped, so a lookup returns a real sample rather than a NaN.

```
DRIFT        = HEADING - HEADING[TIME=first]
ALT_GAINED   = ALTITUDE[TIME=last] - ALTITUDE[TIME=first]
```

The filters take the timestep from the x channel at **every** sample rather than
assuming a fixed rate, so they stay correct on unevenly sampled data. Press
**Help** in the COMPUTE tab for the full reference; an existing formula can be
edited in place rather than deleted and recreated.

Computed parameters may reference other computed parameters. Cycles are detected
and refused when you define them, not discovered at plot time. Removing one also
removes anything defined in terms of it, and says so.

Division by zero yields `NaN`, not infinity — an infinity would silently destroy
a plot's y-range, whereas a `NaN` simply breaks the line where the data is bad.

## HDF5 files

Result files stored as HDF5 open like any other: choose one in the file dialog,
or pass it on the command line. What is read is exactly what is read from an
`.aoe` file — the channels, the runs, and one array per channel per run. Nothing
downstream can tell the difference: decimation, ISO filters, computed
parameters, styles and workspaces all work the same.

This needs **h5py**, which is not part of the base install. Without it, opening
such a file reports `reading HDF5 files needs the h5py package, which is not
installed` and the rest of the program carries on as before.

### Files that declare their own structure

Some exporters say outright what is in the file, and those are read as stated
rather than guessed at:

```
/DOMAIN/OSMA_1/PARAMETERS/ALFA              a channel, with @unit
/DOMAIN/OSMA_1/PARAMETERS/ALFA/ALFA_1_2_0   its samples for one run
/DOMAIN/OSMA_1/SIMULATIONS/SIMULATION_1_2_0 a run, with its sweep values
```

`PARAMETERS` lists the channels and `SIMULATIONS` lists the runs, so a dataset
is simply the two put together and nothing has to be inferred. The units come
from each channel's group, where they are declared once, rather than from every
dataset. Reading this costs two listings per session, one attribute per channel,
and a single dataset opened to learn the sample count — no dataset name is
enumerated at all.

A file holding **more than one session** — `OSMA_1` beside `OSMA_2` — is read
correctly here and cannot be by inference: every session repeats the same run
names, so a reading keyed on the dataset name alone sees `ALFA_1_2_0` twice,
declares itself inconsistent and stands down in favour of a reading that is
consistent and useless. The session is part of the run's identity, which is what
it is, and the runs come out as `OSMA_1/1_2_0`, `OSMA_2/1_2_0` and so on.

### Which datasets are which

For a file that declares nothing, the layout has to be inferred. HDF5 is a
container, not a layout. Two exporters writing the same simulation produce trees
with nothing in common but the file signature, and the thing they disagree about
most is where the identity of a *run* is written. These are the conventions the
reader knows:

```
/RUN_1/ALTITUDE               a group per run, a dataset per channel
/ALTITUDE/ALTITUDE_1_2_0      a group per channel, a dataset per run, with the
                              run spelled into the dataset name
/CASE_2/aero/ALTITUDE         the run further up the tree
/ALTITUDE                     a single run, nothing to disambiguate
```

Only 1-D numeric datasets are considered, and only those of the length shared by
most of them — a short metadata vector alongside the channels is ignored rather
than turned into a channel two samples long.

The reader enumerates every convention, discards the ones that do not partition
the file consistently, and ranks what is left on evidence from the tree itself:
whether each channel's name matches the group it sits in, and whether the run
keys are the same under every group. Both signals say the same thing — that the
run axis is orthogonal to the tree — and together they separate the two readings
that matter, since a group-per-channel file read the other way round yields one
run with twice as many channels, all named `ALTITUDE_1_2_0`.

Which convention was chosen is written to the log at INFO, along with what else
was considered and how it scored. If a file comes out with its runs and channels
transposed, that line is where to look first.

Units are taken from a `units` or `unit` attribute on each dataset when one is
there, and left empty otherwise, exactly as for the packed `.aoe` dialect.

### What is not read

Attributes holding anything other than a unit — masses, inertias, configuration
— are ignored. They are not channels, and there is nowhere in the interface that
a per-run property belongs today.

### How much is read, and when

Opening an HDF5 file reads **no samples at all**. The group tree gives the
channel names, the run names and the shapes, which is everything the DATA tree
and the parameter lists are built from, so a file of any size appears at once.
A column is fetched the first time something asks to draw it: a page of four
tiles against forty channels reads four of them.

Three places a column can come from are tried in order of cost — already in
memory, in the sidecar, then read from the file — so nothing is ever read twice.
An ISO scan is cheaper still: it reads element zero of each run's dataset, one
chunk rather than a column, which is the same shortcut the core takes on a
parsed file through its index.

A moment after the file is on screen, and only for files over 8 MB, a separate
process is started to fetch the samples and write them out as a `.aoec` sidecar
in the layout this program reads fastest. The status bar says so quietly —
`caching 1 file in the background` — and the window is fully usable throughout,
because that process shares no session with it. Every later open of that file is
then served from the sidecar: no reading of the HDF5 at all, and the memory cap
applies normally. If the file changes, its fingerprint stops matching and the
sidecar is ignored, exactly as for a parsed file.

So the trade is: the first open is instant and incremental, one later pass in
another process pays for the sidecar, and from then on opening is the cached
path. Deleting a sidecar only costs speed.

Reload works and goes back through the reader, keeping the file's index and with
it every colour and style keyed on its runs.

### Files on a network share

Reading an HDF5 file over a share is not slow because of the bytes, it is slow
because of the round trips, and working out the layout is where they used to
be. Three things keep that count down.

**An inferred layout is worked out from dataset paths, not from the datasets.**
None of the conventions above look at a dataset's contents — every one of them keys on
the path — so the names in the file are enough to decide which convention is in
force. Enumerating names is one traversal; opening every dataset to ask its
shape is one round trip apiece, and a file of 50 runs × 1000 channels holds
fifty thousand of them. Shapes are read only for the channels of the first run,
to settle the common length and collect the units, plus one dataset of each
other run to confirm it agrees. **1,049 reads instead of 50,000.**

**The layout is then written down,** gzipped, as a `.aoelay` file beside the
source — or in the per-user cache directory when the source's own directory is
read-only, which solver output usually is. Opening the file again reads that
instead of the tree. It is checked three ways: the source must be the size and
date it was, the document must be a format this version understands, and one
dataset it names must still be there with the length it claims. That last check
is a single read, and it is what makes the other two safe to trust. **One read
instead of 50,000.**

This matters most once a sidecar exists. At that point not one sample is read
from the HDF5 file — and the tree was still being walked on every open, because
the core had to be told what the file contains before it could look for a
sidecar. That walk was the whole cost of opening an already-cached file.

**The file is opened once per task, not once per read.** A handle is kept and
reused, so drawing six parameters, or scanning fifty for an ISO filter, costs
one open rather than six or fifty. The handles are released the moment the task
finishes: reads only happen inside a task, so that is the whole span over which
reuse pays, and the viewer never holds a file open while idle — it must never be
the reason a solver cannot write its own output. A handle is also re-checked
against the file's size and date before reuse, because a handle reads the file
it was opened on, which is not necessarily the file at that path any more.

If results live on a share but you would rather the derived files did not,
`AOE_CACHE_DIR` moves both the sidecars and the layout files to a directory of
your choosing.

## The AOE file format

Two dialects exist, and both are read.

**Packed** — names several to a line, no units:

```
*PARAMETRES
 'TIME'    'ALPHA'   'MACH'    'NZ'
*TABLEAU : RUN_001
 0.000000  2.000000  0.600000  1.250000
 0.010000  2.006999  0.600000  1.249980
*TABLEAU : RUN_002
 ...
*FIN
```

**Indexed** — one parameter per line, prefixed by its ordinal and followed by
its unit, usually with an `*ENTITY` block of free text in between:

```
*PARAMETRES
	1	'TIME'		's'
	2	'PARAMETER001'	 	''
	3	'PARAMETER002'	 	'deg'
	4	'PARAMETER003'	 	'deg'
*ENTITY
Any amount of free text here, provenance notes, anything.

*TABLEAU NUM SIMU: 1.2.0
   0.00000E+00   0.00000E+00   6.43096E+00   0.00000E+00  -3.44376E-13
   0.00000E+00   0.00000E+00   0.00000E+00   4.10000E-01   0.00000E+00
   ...
```

- `*PARAMETRES` introduces the channel names, single-quoted. The two dialects
  are told apart by what precedes the first quote on a line: an ordinal, or
  nothing. **In the indexed dialect the second quoted token is a unit, not a
  channel.** Treating it as a channel is not a cosmetic mistake — a
  585-parameter file becomes 1156 parameters, `deg` and `ft` appear in the
  channel list, and every column index shifts by one per unit seen, so `TIME`
  silently returns another channel's data. The file loads, the plots draw, and
  the numbers are somebody else's.
- A parameter with no unit is written `''`. That empty token has to be counted,
  not discarded, or the next line's unit lands on it.
- Units are kept and shown on axis labels, in the parameter list, in STATS and
  in INSPECT — `TIME [s]`, `PARAMETER013 [deg.s-2]`. Computed parameters get no
  unit: deriving one through a formula means dimensional analysis, and a wrong
  unit on an axis is worse than none.
- Each `*TABLEAU` starts a simulation block, with the id taken from whatever
  follows a colon — `RUN_001` or `1.2.0` alike. Without an id, blocks are
  numbered `SIM_001`, `SIM_002`, …
- `*ENTITY` and any other `*` directive ends the current block, and the free
  text under it is ignored. A second `*PARAMETRES` block, which these files
  repeat before every simulation, is skipped rather than re-read.
- Data lines hold one value per channel, whitespace-separated. A record may
  **wrap across several physical lines**, as Fortran writes it when the record
  exceeds the format width; the parser handles this. (Files that wrap are
  parsed on one thread per simulation rather than split into byte chunks: a
  chunk boundary mid-record would misalign every column after it.)

Numbers may be written as `1.5`, `1.5e3`, `1.5E3`, `1.5D+03` (Fortran double) or
`1.5+03` (Fortran with the `E` dropped). Tokens that are not numbers — `NaN`, or
Fortran's `*****` field-overflow marker — become `NaN`, which shows as a gap in
the plot rather than a false zero.

## Scripting without the GUI

The core is usable from Python on its own, with only `numpy` installed — no Qt.

```python
import sys
sys.path.insert(0, "python")

from aoeviewer import Session

with Session() as session:
    f = session.add_file("results/run_042.aoe")

    # One batched, multi-threaded read rather than a load per channel.
    session.preload(f.index, [], ["TIME", "ALPHA", "NZ"])

    session.set_computed("G_LOAD", "NZ * 9.80665")

    for sim in f.simulations:
        t = sim.channel("TIME")          # zero-copy view of the C++ buffer
        g = sim.channel("G_LOAD")
        print(f"{sim.sim_id}: peak {g.max():.2f} m/s^2 at t={t[g.argmax()]:.2f}s")
```

Arrays returned by `channel()` are **read-only views of C++ memory**, not
copies. That is what makes them free. Each view holds a reference to the buffer
behind it, so the memory cap can never free samples something is still reading;
the memory is released when the last view of it goes. They do stop being valid
when the owning file is reloaded or removed, so `.copy()` anything you need to
keep past that.

## Performance

The application is built for files of several hundred megabytes. Two design
choices carry most of that:

**Nothing is read until it is plotted.** Opening a file only indexes it — header
names and the byte range of each run — at 5–7 GB/s. Sample data is parsed
per column, on demand, in parallel.

**Every column carries its own summary.** Extent, gaps and whether the samples
are ordered are worked out in parallel while the column is parsed, in the pass
that already has the data in cache. Auto-scaling then asks a question it used to
answer by rescanning: on a tile of twenty-five curves over 400 000 samples, a
fit costs 0.08 ms instead of 38 ms.

**Curves that share a pen are drawn as one item.** The cost of a pyqtgraph item
is a bounding rectangle, a paint call and a scene-graph node, whether it holds
ten points or a hundred thousand -- so a study of 1200 runs plotted against two
parameters was 2400 items, which the core fills in 35 ms and Qt then spends
minutes on. Curves that look identical cannot be told apart on screen anyway, so
they are concatenated into a single polyline with a NaN between consecutive
runs, which `connect="finite"` renders as a break rather than a stroke across
the plot. Twelve palette colours turn 2400 items into twelve.

Each curve remains its own entry in the tile's model: click-to-inspect, the
crosshair readout, marker dots, area segments and the CSV export all still
answer "which run, which parameter". Merging is a drawing decision and nothing
more.

**The legend is capped at 60 rows**, then says how many were left out.
pyqtgraph builds a `QGraphicsGridLayout` with two items per row, so a
thousand-run legend asked Qt to lay out several thousand graphics items in one
column -- which is where the window stopped responding rather than merely
slowing down.

**Nothing full-resolution reaches Python.** The core decimates every curve to
roughly two points per horizontal pixel before it crosses the boundary, so a tile
draws ~1200 points whether the channel holds ten thousand samples or ten million.

**Turning a 3D cube only re-projects it.** A rotation changes two angles and
nothing else, so that is all it costs: the normalised cube and the pen
assignment are cached, and a rotation re-projects into the draw items already
on the tile rather than re-reading three channels per run, recomputing their
bounds, re-thinning the samples and rebuilding every item. At 25 runs of 1 814
projected points that is **0.7 ms** of arithmetic per step instead of 5.2 ms,
before counting the Qt items it does not build and throw away.

**A redraw that changes nothing costs nothing.** Once a page holds a lot of
data, what makes the window feel slow is not drawing a curve but deciding to
draw one that is already on screen. Four things were doing exactly that, and
each of them was triggered by an ordinary click:

- *The active-tile border repainted the whole page.* `QWidget.setStyleSheet`
  does no comparison of its own — handed the string it already has, it still
  repolishes the widget and schedules a repaint, and a tile is a
  `QGraphicsView`, so that repaint is its entire scene. The border was reapplied
  to every tile on every mouse press, because a press announces the tile whether
  or not the active one changed. A 5x5 page therefore redrew twenty-five plots
  holding a million points between them to change a border on two. It is now
  applied only when the state actually flips.
- *Every rebuild threw away every draw item.* A rebuild arrives for many reasons
  that say nothing about the data: restyling a curve, toggling the grid,
  dragging a marker, coming back to a page. Each one dropped every item and
  re-decimated every curve from full resolution for an answer identical to the
  one already on screen. Groups that draw exactly the same curves from exactly
  the same buffers are now kept, with their pen updated in place — the points
  are recognised as current and never recomputed. At 150 curves over 10.6 M
  samples, restyling a curve went from **46 ms to 1.1 ms per tile**.
- *Every redraw went through a worker thread.* Starting a background task
  disables the panels, the rail and the whole plot grid and re-enables them a
  moment later, and every plot widget repaints on each of those. A style tweak
  was paying for two full-grid repaints, a thread and two trips round the event
  loop before a curve was redrawn — to cover a read that had nothing to read.
  A redraw whose channels are already resident now draws straight away.
- *The style table rebuilt its widgets on every click.* It holds one row per
  curve, and each row is a colour button and two populated combo boxes; in
  simulation mode a study of a few hundred runs created and destroyed a
  four-figure number of widgets to answer a click that usually changed nothing
  in the table. Rows are now refilled in place, and a refresh that would produce
  the same rows returns without touching a widget.

The decimation cache behind the second of those is keyed on the view as well as
the samples, and getting that key wrong is easy: quantising only the endpoints
hid every zoom whose lower edge scaled with its width, so zooming in around the
origin kept whatever resolution the curve already had. The key and its
arithmetic live in `aoeviewer/scales.py`, which imports no Qt, and are tested in
`tests/test_redraw.py`.

**Colouring by ISO does not load the ISO column.** `iso_values()` reads the
first record of each block through the index and touches no column memory — the
683x saving described below. Naming the ISO parameter as a channel the tile
needed undid exactly that, parsing the whole of MACH across every run of a
550 MB file to answer a question the header had already answered.

**A file opened once is opened fast afterwards.** An AOE file stores one record
per line — every parameter of one time step, side by side — and this program
reads the transpose of that: one parameter, every run. So plotting a single
channel makes the parser walk the whole file and run a float parser over every
value it then throws away.

The first time a file over 8 MB is opened, a `.aoec` sidecar is written beside
it holding the same numbers the other way round: all runs of TIME, then all runs
of the next channel, as raw `float32`, with each run's offset and each block's
minimum and maximum in a header. Opening then maps that file instead of scanning
the source, and loading a column is a copy out of the mapping rather than a
parse. See [The `.aoec` sidecar](#the-aoec-sidecar) below.

Measured on three 550 MB files of **simulated flight data** (1.66 GB, 75 runs,
38 channels each) on a small container with three worker threads:

| | |
|---|---|
| Open all three (index scan only) | 0.45 s, up to 4.7 GB/s |
| First plot: 4 channels x 75 runs, cold | 1.37 s, 1.2 GB/s |
| Decimate 225 curves (15.9 M samples) to 1200 px | 34 ms |
| Redraw on pan or zoom (225 curves) | 8 ms |
| ISO value scan across all files | 1 ms |
| Cached channel lookup | 26 ns |
| Computed channel over 75 runs, cold | 60–190 ms |
| Resident memory, 4 channels x 75 runs | 108 MB |
| Resident memory, every channel of every run | 1024 MB |

The decimation is a 60x reduction: 15.9 M samples become 266 k points, and that
is what reaches the plot widget.

Three things were fixed after measuring rather than guessing:

1. **ISO scanning was reading whole columns.** An ISO parameter is constant
   within a run, so its value is the first sample — but the obvious
   implementation loaded the column to get sample zero, costing a full scan of
   the file per parameter (1.37 s). Reading just the first record of each block
   made it **683x faster** and it now touches no memory at all.
2. **Skipping unwanted columns dominated selective reads.** Reading one column
   of twenty-four cost 90% of what reading all of them cost, because finding
   token boundaries examined every byte individually. Word-at-a-time scanning
   made selective loads **1.7x faster**.
3. **Loading blocked the window.** File opening and channel loading now run on a
   worker thread — `ctypes` releases the GIL for the duration of a core call, so
   the event loop keeps running while the core uses every worker thread inside
   it. The status bar shows progress and the panels disable, rather than the
   window greying out.

**Memory.** Cached sample data is capped (2 GB by default, `--memory-limit MB`).
Beyond the cap, least-recently-used columns are dropped and re-read when needed
again, so the only cost of the cap being wrong is time. The status bar shows the
current cache size.

To reproduce the numbers:

```bash
make flightdata                       # three 500 MB simulated flights, ~3 min
python tools/bench_app.py data/flight_*.aoe
```

### The test data is a flight, not noise

`tools/gen_flight_data.py` integrates an aircraft rather than emitting sine
waves, because synthetic data lets a viewer look correct while being wrong in
exactly the ways that matter here. Noise has no transients, so decimation
appears lossless whatever it does; every channel has the same shape, so a wrong
column index is invisible; and nothing is constant per run, so ISO filtering has
nothing to key on.

The model is longitudinal rigid-body dynamics with a pitch-rate autopilot and a
point-mass lateral model, on an ISA atmosphere:

```
V̇ = (T cos α − D)/m − g sin γ        γ̇ = (L cos φ + T sin α − mg cos γ)/(mV)
q̇ = M / I_yy                          θ̇ = q,   α = θ − γ
ψ̇ = g tan φ / V                       ḣ = V sin γ
```

with a drag polar and a pitching moment whose static stability follows the
centre of gravity, `C_mα = C_Lα (x_cg − x_ac)/c̄` — so moving the CG aft
genuinely reduces the short-period damping, and the runs differ in ways a flight
test engineer would recognise rather than in a random seed. Runs are integrated
together as NumPy arrays (one Python-level loop per *time step*, not per
sample), which is why 500 MB takes about a minute rather than an hour.

Elevator doublets at four points in each run excite the short period. Those
spikes are the reason min/max decimation exists: a stride-sampled viewer loses
them entirely, and this data will show you that it has.

Written channels include `TIME, ALPHA, BETA, THETA, PHI, PSI, GAMMA, P, Q, R,
ALTITUDE, SPEED, MACH, EAS, DYNAMIC_PRESSURE, EXTERNAL_TEMPERATURE,
AIR_DENSITY, NX, NY, NZ, MASS, CG, FUEL_FLOW, THRUST, DRAG, LIFT, ELEVATOR,
AILERON, RUDDER, THROTTLE` and the three inertial position components, plus five
per-run constants (`INITIAL_MASS`, `CG_REF`, `CL_ALPHA`, `THRUST_RATING`,
`CONFIGURATION`) for the ISO tab to key on.

## The `.aoec` sidecar

A sidecar is a binary rewrite of an AOE file in the order this program reads it.
It is written automatically the first time a file over 8 MB is opened, lands
beside the source as `run.aoe.aoec`, and is used on every open after that.

Nothing depends on it. Delete one and the file opens exactly as it always did,
only slower. It is never the only copy of anything: every number in it came out
of the `.aoe`, and every path that reads it falls back to parsing the text.

### What it holds

```
Header            128 bytes: the format version, the source's fingerprint,
                  and where each section below begins
Column records    one per parameter: its name and unit
Run records       one per run: its id, and the byte range it occupied
                  in the source, so a fallback needs no fresh index scan
Block records     one per (parameter, run): where its samples are, how
                  many, and their minimum, maximum, and whether they
                  contain gaps or are monotonic
Samples           float32, parameter-major:
                    parameter 0: run 0, run 1, ... run N-1
                    parameter 1: run 0, run 1, ... run N-1
```

Three of those earn their place:

- **Parameter-major** means the samples for "this channel, every run" are one
  contiguous region. Reading a channel is one sequential read instead of a walk
  over the whole file with 31 values discarded for every one kept.
- **Run offsets in the header** mean opening does not scan. On a 1200-run file
  the index scan was two thirds of the time between choosing a file and seeing
  a plot.
- **Minimum and maximum per block** are computed once, when the sidecar is
  written. Auto-scaling asks for them on every redraw and now never rescans.

### Who writes it, and when

A separate process, started once the file is already open and on screen. It has
to be: writing a sidecar is a second full pass over the file, and the core holds
its write lock for the whole of it, so on a worker thread inside the application
every panel and plot that wanted a channel queued behind it and the window
stayed disabled until it finished — about five minutes for a 2.9 GB HDF5 file.
A separate process shares no session, so there is nothing to queue behind: the
status bar says `caching 1 file in the background` and the window stays usable.

It can also be run on its own, to warm a directory of results before anyone
opens them:

```
aoeviewer --build-cache run_001.aoe run_002.hdf5
```

Either way it opens the source read-only, writes nothing but the sidecar, holds
no lock that would stop a solver writing to the source, and if the source
changes while it works it abandons the sidecar and deletes it rather than leave
one that mixes the file's before and after. The source itself is never modified
or deleted under any circumstance.

### How staleness is caught

A sidecar that disagrees with its source would put numbers on screen that are
not in the file any more, so three independent properties of the source are
recorded and **all three** must match before a byte of it is trusted:

| | catches | missed by itself |
|---|---|---|
| Length | truncation, extension, an append | an in-place rewrite of the same length |
| Modification time | an in-place rewrite | anything that restores timestamps — `rsync --times`, a restore from backup |
| Content hash | a rewrite that preserves both of the above | nothing relevant; it is the backstop |

The hash covers the whole file below 4 MB. Above that it covers 64 evenly
spaced 64 KB windows, always including the first and last — a fixed 4 MB of
reading however large the file is, which costs about 6 ms and does not grow.
Hashing half a gigabyte in full would cost more than the parse the sidecar
exists to avoid.

The check is deliberately strict in the direction that only ever wastes time: a
false negative rebuilds the sidecar, a false positive shows wrong data. A file
copied to another machine gets a new modification time and so is re-cached, even
though its contents are identical. That is the intended trade.

A sidecar is also refused outright if it is truncated, if its header hash does
not match, if any of its offsets fall outside it, if it was written by a
different format version, or if it was written on a machine of the opposite byte
order.

### Where it goes

Beside the source first, so copying a results directory copies its caches and
deleting the results deletes them. Solver output often sits on a read-only
share, so a per-user directory is tried second:

| | |
|---|---|
| Windows | `%LOCALAPPDATA%\aoeViewer\cache\` |
| macOS | `~/Library/Caches/aoeviewer/` |
| Linux | `$XDG_CACHE_HOME/aoeviewer/`, else `~/.cache/aoeviewer/` |

The source's full path is hashed into the name there, so two files called
`results.aoe` in different directories do not share one.

Failing to write a sidecar is never reported. It is an optimisation nobody
asked for; the file has already opened and works.

### Controlling it

| | |
|---|---|
| `AOE_CACHE=0` | never read or write sidecars |
| `AOE_CACHE_DIR=<path>` | use this instead of the per-user directory, for sidecars and for HDF5 layout files alike |

From a script:

```python
from aoeviewer import Session

session = Session()
session.add_file("results/run_042.aoe")

session.cache_active(0)     # is this file being served from a sidecar?
session.cache_path(0)       # where it is, or ""
session.build_cache(0)      # parse once and write one (costs a full parse)
session.discard_cache(0)    # delete it and go back to reading the text
```

`build_cache` holds one parameter across every run in memory at a time,
whatever the file's size, so it is safe to call on the largest files this is
meant for.

### What it is worth

A generated 73 MB file, 1200 runs of 1000 rows over six channels, opened and
then plotted against two parameters with an ISO scan:

| | text | sidecar |
|---|---|---|
| Open (index) | 213 ms | 22 ms |
| Preload 2 channels x 1200 runs | 81 ms | 7 ms |
| Fetch 1200 curves | 6 ms | 5 ms |
| ISO scan | 7 ms | 0.3 ms |
| **Total** | **306 ms** | **32 ms** |

Writing the sidecar took 0.24 s once. It is 27.7 MB against the source's
73.1 MB — `float32` is more compact than the decimal text it came from.

The advantage widens with file size: the sidecar's open cost is dominated by
the fingerprint, which is capped, while the parse it replaces is not.

## Testing and benchmarking

```bash
make test                                  # 1687 C++ checks
python -m unittest discover -s tests -v    # 415 Python tests
make bench                                 # parser microbenchmark
python tools/bench_app.py FILE...          # end-to-end, on real files
```

The Python tests use stdlib `unittest`, not pytest, so they run on a machine
where nothing extra can be installed.

`tests/test_bindings.py` checks that each operation does the right thing when
called correctly. `tests/test_monkey.py` checks something different and, in
practice, more valuable: that **no sequence of legal operations can put the
application into a broken state**. It runs tens of thousands of randomised
operations — adding and removing files, pages and tiles, markers, areas, ISO
selections, formulas and aliases — and asserts the invariants after each batch:
no selection may name a run that no longer exists, no tile range may be
inverted, the active tile must stay addressable however the grid is resized.

That is a different class of bug from a wrong return value, and the two hardest
ones found here were both of it: a removed file leaving selections pointing at
indices that had shifted, and a tile keeping parameters that no longer existed.
Neither is reachable by calling one function wrongly; both are reachable by
calling three correct functions in the wrong order. Every case is seeded, so a
failure replays exactly.

`tests/test_redraw.py` covers the part that decides whether the window feels
fast: not how a curve is drawn, but how often the code decides to draw one that
is already on screen, and how much of the widget tree it disturbs to answer a
click that changed nothing. PySide6 is a large binary wheel and a plot widget
needs a display, so `tests/qt_stubs.py` stands in for PySide6 and pyqtgraph —
recording what was asked of them and nothing more, which is enough for questions
of the form *"given this state, does it do the expensive thing?"*. The stubs are
installed unconditionally: an answer about our own code must not depend on
whether the machine running the suite happens to have Qt.

`tests/test_construction_order.py` complements both by *parsing* the GUI rather
than importing it, which is how the wiring is checked on a machine with no Qt at
all.

Arithmetic that a mistake could hide in lives in its own Qt-free module, so it
can be tested directly: `aoeviewer/scales.py` for the draw budget and the
log-axis conversion, `aoeviewer/isogroups.py` for editing ISO intervals. The
second is checked twice over — case by case in `test_redraw.py`, and by a few
thousand random boundary edits in `test_monkey.py` asserting that the intervals
come out ordered and touching whatever was typed into them.

### Sizes

Every size in the interface is in `aoeviewer/theme.py`, because they only work
as a set: shrinking the panels but not the tiles, or the text but not the
padding around it, gives you a smaller-looking application that is no less
crowded. Widget text is sized in pixels (`FONT_PX`, `FONT_SMALL_PX`) and the
plots in points (`PLOT_TITLE_PT` and friends, roughly 0.75x at the 96 dpi Qt
assumes) because that is what each side wants; `plot_font()` is how the drawing
code asks for one.

Sizing widget text in pixels has one consequence worth knowing about: it makes
`QFont.pointSizeF()` report **-1**, so a font read back off a widget cannot be
adjusted relative to its current size — the adjustment silently falls back to
whatever default the caller named. Every size here is therefore stated outright
rather than derived from another one.

Indicative benchmark figures (4-core container, 3 worker threads):

```
1 run x 500000 rows   (19.0 MB)
  index scan          0.008 s    2302 MB/s
  parse 4 columns     0.025 s     769 MB/s    81 M samples/s
  cached lookup        26 ns per call

64 runs x 20000 rows  (47.6 MB)
  index scan          0.022 s    2165 MB/s
  parse 4 columns     0.081 s     586 MB/s    63 M samples/s
```

## Architecture

```
python/aoeviewer/ui/      Qt widgets       PySide6 + pyqtgraph
python/aoeviewer/ui/icons.py  toolbar icons, drawn not loaded
python/aoeviewer/model.py application state, no Qt, no core
python/aoeviewer/projection.py  3D projection maths, no Qt
python/aoeviewer/session.py  Pythonic API
python/aoeviewer/_core.py    ctypes bindings
          |
          |  C ABI  (core/include/aoe/aoe_c_api.h)
          v
core/src/session.cpp      files, aliases, computed channels
core/src/dataset.cpp      indexing and lazy parallel column loading
core/src/formula.cpp      expression compiler and evaluator
core/src/decimate.cpp     min/max plot decimation
core/src/iso.cpp          ISO grouping
core/src/mapped_file.cpp  portable mmap
```

**Why a C ABI and ctypes rather than pybind11.** A pybind11 module is compiled
against one specific Python ABI and must be rebuilt for each version; it also
requires pybind11 at build time, which is not installable on every machine. A
plain C shared library has neither problem, and the call overhead is irrelevant
here because calls are coarse — load a file, fetch a column, decimate a series —
each doing milliseconds of work.

**Why decimation is the centrepiece.** A tile 600 px wide cannot display more
than ~600 distinct x positions, so the core reduces every curve to roughly two
points per pixel before it crosses into Python. A million-sample channel becomes
~1200 points. Min/max bucketing rather than stride sampling means narrow spikes
survive at any zoom level — on flight-test data those transients are usually the
point. Redecimation happens on range change, so zooming in reveals real detail.
This is what keeps a Python front end fast enough for this job.

**Notable changes from the previous version.** Beyond going cross-platform, the
following were bugs rather than ports:

- The float parser accumulated fractional digits one at a time and drifted;
  Fortran `D` exponents were unreadable; a trailing `+`/`-` was misparsed as an
  exponent; malformed tokens became `0.0` and plotted as a fake zero line.
- Formulas were re-parsed for every simulation, and raw `float*` pointers were
  baked into the AST — those dangled as soon as a later column load reallocated
  the vector behind them.
- Parsing parallelised over simulations only, so a file containing one large
  table used a single core. It now also splits byte ranges within a block.
- Each parse task searched the simulation list for the next block's offset, and
  re-tested every data line for the terminator; both are precomputed during the
  index scan now.
- Failed column loads pushed a fake `0.0` sample to stop the UI retrying every
  frame. Failures are now recorded as such, and missing data reads as missing.
- The workspace format was ad-hoc delimited text that broke on any path or
  parameter name containing the delimiter. It is JSON now.

## When something goes wrong

Every failure is written to **`aoeviewer.log`**, beside the application (or in
`~/.aoeviewer` if that directory is read-only, which a frozen build's often is).
It captures unhandled exceptions on any thread, failures inside background
tasks, and Qt's own warnings, and records the version, platform and library
paths at startup. `python -m aoeviewer --version` prints where it is being
written. Send that file with any bug report; it is usually the whole story.

## Troubleshooting

**`could not find the aoeViewer core library`** — the core has not been built,
or it is somewhere unexpected. Run `make` or `build.bat`; the error lists every
directory that was searched. `AOEVIEWER_CORE` overrides the search.

**`Could not find module ...aoecore.dll (or one of its dependencies)`** — the
DLL is present but something it links against is not. Windows never says which,
so ask objdump:

```bat
objdump -p build\\aoecore.dll | findstr "DLL Name"
```

Anything beyond `KERNEL32.dll` and `msvcrt.dll` — typically
`libwinpthread-1.dll`, `libstdc++-6.dll` or `libgcc_s_seh-1.dll` — means the
MinGW runtime was linked dynamically. Rebuild with `build.bat`, which passes
`-static -static-libgcc -static-libstdc++`. Note that `-static-libgcc
-static-libstdc++` **alone are not enough**: static libstdc++ still references
`libwinpthread-1.dll` on a posix-threads MinGW, so plain `-static` is required
as well.

**`Importing the numpy C-extensions failed`, from the frozen build only** — the
bundle is missing something NumPy links against, or is forbidden from loading
it. Run `aoeviewer --selftest` (or rebuild, which runs it for you) to get the
real error rather than the truncated dialog, then:

- If it says `DLL load failed while importing _multiarray_umath`, the support
  DLLs beside the `numpy` package were not collected. The spec collects
  `numpy.libs` explicitly, so rebuild with `--clean` to discard a stale
  `build/pyinstaller` cache from before that change.
- If the self-test passes but a double-click still fails, the machine is
  blocking execution from the unpack directory. Use the folder build, or
  `--onefile --runtime-tmpdir "%LOCALAPPDATA%\aoeviewer"`.
- If NumPy 2.x is installed, an old PyInstaller may still be looking for
  `numpy.core` rather than `numpy._core`. `pip install -U PyInstaller`.

**`ModuleNotFoundError: No module named 'aoeviewer'`** — `python/` is not on the
import path. Set `PYTHONPATH=python`.

**`ModuleNotFoundError: No module named 'colorama'`** — a consequence of
installing with `--no-deps`; pyqtgraph imports it at runtime. Fetch that one
wheel and install it the same way.

**`is not a supported wheel on this platform`** — wrong wheel for your
interpreter. See [Offline or behind a proxy](#offline-or-behind-a-proxy);
`pip debug --verbose` lists the tags that will be accepted.

**Plots are slow** — check that the tiles are actually decimating. Ten curves in
a 600 px tile should be drawing about 12,000 points regardless of file size. If
a channel is not monotonic in x, range-restricted decimation falls back to
scanning the whole series, which is slower but still correct.

**A channel plots as a flat line at zero** — in the previous version that was
usually a failed load being masked by an injected `0.0`. This version leaves
missing data missing, so a flat zero line now means the file really does contain
zeros.
